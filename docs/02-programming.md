# 02 编程能力

编程是 CS 的手。数学是脑，系统是骨架，编程是把想法变成现实的手。这一章不讲某一门语言的语法——语法一周就能查会。这一章讲的是**作为职业能力，编程到底包括什么**。

## 2.1 至少精通一门语言

“精通”的标准不是“写过 Hello World”，而是：

- **不查文档能写出正确的中等复杂度程序**。语法、标准库常用部分、惯用写法都在脑子里。
- **知道这门语言的边界**：它擅长什么、不擅长什么、常见的坑在哪（比如 Python 的 GIL、JavaScript 的 `this`、C 的未定义行为、Go 的带类型 nil 接口——接口本身非空，里面装的是一个 nil 指针）。
- **能解释语言的设计选择**：为什么这门语言是这样而不是那样（比如“为什么 Go 没有泛型直到 1.18”、“为什么 Rust 要有借用检查器”）。能讲清设计取舍，才算真懂。
- **能读这门语言写的生产级代码**，而不是只读过教科书上的玩具例子。

**选哪一门？** 建议从这三类里选一门作为主语言：

| 类型 | 代表 | 适合 |
|---|---|---|
| 系统级 / 编译型 | C、Rust、Go、Java、C++ | 想走系统、后端、infra 方向；想真正理解计算机怎么工作 |
| 应用级 / 动态 | Python、JavaScript/TypeScript | 想走 AI、数据、前端、快速开发方向 |
| 教学语言 | Scheme、Haskell（了解即可） | 想打深编程语言理论的地基 |

**合格线**：一门语言达到上面的“精通”标准，第二门语言能在一周内上手写可用代码。

**常见误区**：

- 简历上写“精通八门语言”。面试官问深三个问题就露馅。一门真精通，胜过八门都“了解”。
- 只学语法，不学语言的生态：包管理、构建工具、测试框架、调试器、性能分析工具——这些才是日常工作中 80% 的时间花在哪。
- 用一门语言的习惯写另一门语言（比如用 Python 的写法写 Go）。每门语言有自己的惯用风格，入乡要随俗。

## 2.2 编程范式：不止一种思维方式

合格的 CS 至少要理解四种范式，并能说出它们各自解决什么问题：

- **命令式 / 过程式**：一步一步告诉机器做什么。所有语言的地基。
- **面向对象**：用对象和消息组织复杂系统。理解封装、继承、多态——以及它们各自的代价（继承是最容易被滥用的机制）。
- **函数式**：把计算看成函数求值，不可变数据、高阶函数、递归。理解它能帮你写出更易推理的代码，也要知道它在性能上的代价。
- **并发 / 异步**：线程、协程、消息传递、Actor 模型。现代程序绕不开并发，理解“共享可变状态是万恶之源”。

**合格线**：每种范式至少写过一个千行级别的程序；能解释“这个问题用面向对象好还是函数式好，为什么”。

**推荐资源**：

- Harold Abelson、Gerald Jay Sussman《计算机程序的构造和解释》（SICP）——范式思维的启蒙，读完看问题的方式会变
- Robert C. Martin《代码整洁之道》（Clean Code）——面向对象实践的常识
- Bruce A. Tate《七周七语言》（Seven Languages in Seven Weeks）——快速体验多种范式的味道

## 2.3 调试：最被低估的核心能力

会写代码的人很多，会调试的人很少。调试能力的合格线：

- **会用调试器**：断点、单步、查看变量、调用栈——而不是只会 `print`。`print` 调试在简单场景够用，但在并发、递归、状态机问题面前基本失效。
- **会读错误信息**：堆栈跟踪、编译错误、日志——第一反应是读，而不是复制到搜索引擎。90% 的错误信息已经把原因写出来了。
- **会二分定位**：问题出现在一万行代码里，能用二分法、注释法、最小复现把它缩小到十行以内。
- **会复现**：修 bug 之前先写一个能稳定复现它的最小用例；修完之后这个用例变成回归测试。
- **知道什么时候停下来**：调了两小时没进展时，懂得换方法——去散步、讲给别人听（小黄鸭调试法）、或者把问题拆得更小。

**常见误区**：改一行、跑一次、看运气——“霰弹枪式调试”。每次改动都应该有一个假设：“我认为原因是 X，改了 Y 之后应该看到 Z”。没有假设的改动，只是在浪费时间。

**推荐资源**：

- David J. Agans《调试九法》（Debugging）——九条规则，薄薄一本，专治“改一行、跑一次、看运气”

## 2.4 测试：代码质量的底线

- **会写单元测试**：知道什么是好的测试（快速、独立、可重复、断言明确），会用测试框架（pytest、JUnit、Go testing 等）。
- **理解测试金字塔**：单元测试最多、集成测试其次、端到端测试最少。不要倒置。
- **会写回归测试**：每个修掉的 bug 都留下一个测试。
- **知道测试的边界**：测试证明的是“这些用例通过了”，不是“程序正确”。100% 覆盖率不等于没有 bug——覆盖率只度量“跑到没跑到”，不度量“断言对不对”。

**合格线**：自己写的项目有测试，核心逻辑覆盖率在 80% 以上；能说出“这段代码为什么难测，以及我是怎么让它可测的”。

**推荐资源**：

- Roy Osherove《单元测试的艺术》（The Art of Unit Testing）——怎么写好测试、怎么处理难测代码
- 所用语言测试框架的官方文档（pytest / JUnit / Go testing）——先读官方文档里的最佳实践一节

## 2.5 代码质量：写给人看的代码

- **可读性优先**：名字起得准、函数短、一个函数只做一件事。代码是写给人看的，顺便让机器执行。
- **会重构**：能识别坏味道（超长函数、重复代码、过深嵌套、到处传参的全局状态），并知道对应的重构手法。
- **会写文档**：README 说清“这是什么、怎么跑、怎么用”；复杂逻辑配注释说清“为什么这样做”，而不是“在做什么”（代码本身已经说了在做什么）。
- **遵守约定**：风格指南、lint、格式化工具——不要在风格上浪费团队的注意力。

**推荐资源**：

- Robert C. Martin《代码整洁之道》
- Martin Fowler《重构：改善既有代码的设计》
- 《Google 编程风格指南》对应语言版本——直接抄工业界的约定

## 2.6 读代码：比写代码更重要的能力

工作中 80% 的时间在读代码，不是写代码。读代码能力的合格线：

- **能读懂一个中等规模的开源项目**：从 README 和入口开始，沿着调用链画出结构图，知道数据怎么流动。
- **会用工具读代码**：跳转定义、找引用、看调用关系图——而不是用眼睛逐行扫。
- **能评价代码**：读完能说出“这段写得好在哪、坏在哪、如果我来写会怎么改”。
- **从零实现是最好的读代码练习**：从零实现一个小语言、一个数据库、一个 HTTP 服务器——实现过程中，你会读大量参考实现，并且第一次真正理解“为什么工业实现要那样写”。

**推荐资源**：

- 《Crafting Interpreters》（Robert Nystrom，免费在线）——从零写一个语言，是理解语言实现最好的路径
- 《数据库系统概念》配套实验 / 从零写一个简单的 KV 存储
- 阅读源码建议：Redis、SQLite、Go 标准库的 `net/http`——代码量适中、质量极高

## 自测题

1. **不查文档写程序**：用你的主语言，不查任何文档，写一个带测试的命令行待办工具（增、删、改、查 + 落盘存储），核心逻辑测试覆盖。验证：程序跑通、测试全绿；写完后对照文档检查：有没有用到你其实记错的 API？
2. **重构旧代码**：找一段自己半年前写的程序，把函数平均长度减半、消灭所有重复代码，功能不变、测试全绿。验证：重构前后跑同一套测试，结果一致；能说出每一处改动的理由。
3. **读代码**：选一个中等规模的开源项目（比如 Redis、SQLite），从 README 和入口出发，画一张模块结构图，并向别人讲 10 分钟“数据是怎么流过这个系统的”。验证：听的人能复述出主要模块和数据流向。

## 本章总结

| 能力 | 合格的标志 |
|---|---|
| 语言精通 | 一门语言不查文档能写中等复杂度程序，能讲清设计取舍 |
| 编程范式 | 四种范式都写过千行程序，能为问题选范式 |
| 调试 | 会调试器、会二分定位、修前先复现 |
| 测试 | 自己的项目有测试，核心逻辑覆盖率 80%+ |
| 代码质量 | 别人读你的代码不骂人 |
| 读代码 | 能读懂中等规模开源项目，能画出结构图 |

**一句话**：编程能力的合格线不是“会写”，而是“写得出、调得动、测得了、别人读得懂”。
