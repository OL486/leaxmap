# 05 软件工程

前面四章讲的是“一个人能写出正确的程序”。这一章讲的是“**一群人怎么长期维护一个能用的系统**”。这是学校里最容易被忽视、工作中最先被考验的能力：一个人写代码和十个人写代码，完全是两回事。

## 5.1 Git：不是“保存按钮”，是协作的基础设施

**合格线**：

- 基础操作：clone、add、commit、push、pull、branch、merge、stash——不靠图形界面也能完成
- 分支策略：知道 feature branch / Git Flow / trunk-based 各自适合什么场景
- 解决冲突：能处理合并冲突，知道冲突产生的根本原因（同一行被两个人改了）
- 写好提交信息：每个提交只做一件事，信息写清“为什么改”，而不是“改了什么”（diff 已经说了改了什么）
- 会用 rebase 整理提交历史，知道 rebase 和 merge 的区别，以及“不要 rebase 已经推到公共分支的提交”

**优秀线**：会写有意义的 PR 描述（背景、改动、测试、风险）；会做 bisect 定位引入 bug 的提交；理解 monorepo 和多仓库的取舍。

**常见误区**：把 Git 当成网盘——一个提交里塞几十个文件、提交信息写“fix”或“update”。提交历史是给未来的自己和同事看的，不是给机器看的。

## 5.2 设计模式：前人的经验，别重复发明

设计模式不是“必须用的套路”，而是“前人总结的常见解法”。合格线：

- **理解模式解决的问题，而不是背 UML 图**。每个模式先问：它解决什么问题？代价是什么？不用它会怎样？
- **必须掌握的模式**（会识别、会用、会讲清取舍）：
  - 创建型：工厂方法、单例（以及“单例是最容易被滥用的模式”）、建造者
  - 结构型：适配器、装饰器、代理、外观、组合
  - 行为型：观察者、策略、命令、模板方法、状态
- **知道什么时候不该用模式**：为了用模式而用模式，是初学者最常见的过度设计。简单的 if-else 能解决的问题，不要上策略模式。

**推荐资源**：

- Erich Gamma《设计模式：可复用面向对象软件的基础》（GoF）——原典，读重点模式即可
- 《Head First 设计模式》——更易读的入门书
- Robert C. Martin《敏捷软件开发：原则、模式与实践》——把模式放回工程语境里讲

## 5.3 架构：从“能跑”到“能长大”

**合格线**：

- 分层思想：表现层、业务层、数据层——知道每一层该放什么、不该放什么
- 模块化：高内聚、低耦合——能判断“这两个模块该不该拆开”
- 常见架构风格：单体、微服务、事件驱动、分层、六边形架构——知道各自的适用场景和代价（微服务不是银弹，单体在小团队里往往是正确选择）
- API 设计：REST 的基本原则、版本管理、错误处理、幂等性
- 可观测性：日志、指标、追踪——系统出问题时，你能找到原因，而不是靠猜

**优秀线**：能为一个真实项目做技术选型并讲清理由（“为什么用关系型数据库而不用 NoSQL”、“为什么这个服务要拆出来”）；理解 CAP 定理和分布式系统的基本取舍。

**常见误区**：上来就画微服务架构图。一个三人团队的项目用微服务，是用分布式系统的复杂度换取根本不需要的扩展性。

## 5.4 工程实践：让质量成为默认

- **持续集成（CI）**：每次提交自动跑测试、lint、构建。合格线：自己的项目接了 CI，测试失败时提交会被拦下来。
- **代码评审（Code Review）**：会提 PR、会审 PR。评审的重点是“逻辑对不对、边界全不全、名字起得准不准”，不是“这个空格该不该有”（那是格式化工具的事）。
- **文档**：README、架构文档、API 文档、变更日志（CHANGELOG）。合格线：别人能照着 README 把你的项目跑起来，不用来问你。
- **依赖管理**：知道依赖的版本、许可证、更新策略。不要把来路不明的依赖引进来。
- **安全意识**：不把密钥提交进仓库、知道 SQL 注入和 XSS 是怎么回事、输入校验是必须的。

**推荐资源**：

- 《Google 软件工程》（Software Engineering at Google）——免费在线，大规模工程实践的集大成
- Jez Humble《持续交付》（Continuous Delivery）——CI/CD 的经典
- 《凤凰项目》（The Phoenix Project）——用小说讲 DevOps，读着不累

## 5.5 开源协作：最好的简历和最好的学校

**为什么重要**：开源协作同时锻炼三件事——读代码、写代码、和人协作。而且它是公开的、可验证的：面试官能直接看到你写的代码和讨论问题的过程。

**合格线**：

- 会用 GitHub 的完整工作流：fork、提 PR、回应 review、处理 CI 失败
- 能给一个开源项目提一个有意义的 PR（修 bug、补测试、改文档都算），并走完评审流程
- 会写好的 issue：复现步骤、期望行为、实际行为、环境信息——缺一个，维护者就得多问一轮

**优秀线**：长期维护一个自己的开源项目（哪怕很小）；能参与一个中型项目的讨论和设计；理解开源许可证的区别（MIT / Apache / GPL）。

**常见误区**：

- 只想着“给大项目提 PR 镀金”，却不愿意从修文档、补测试这些小事做起。维护者最欢迎的，恰恰是这些小事。
- 提 PR 之前不读贡献指南（CONTRIBUTING），不跑测试，不遵守代码风格——这是最快被拒绝的方式。

## 本章总结

| 能力 | 合格的标志 |
|---|---|
| Git | 分支、合并、rebase、写好提交信息，协作不添乱 |
| 设计模式 | 掌握十几个核心模式，知道什么时候不该用 |
| 架构 | 能分层、能模块化、能为项目做技术选型并讲清理由 |
| 工程实践 | 自己的项目有 CI、有测试、有文档、有 CHANGELOG |
| 开源协作 | 走完过一次完整的 PR 流程，从 fork 到合并 |

**一句话**：软件工程的合格线不是“知道这些概念”，而是“在一个真实项目里实践过它们，并且留下了别人能接手的痕迹”。
